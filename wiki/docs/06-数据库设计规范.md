## 1. 事实来源与适用范围

数据库设计规范说明新增或调整结构时应如何处理；源码映射说明代码期望什么；数据库元数据才说明目标实例实际具有什么。三者需要相互核对，不能互相替代。

| 材料 | 可以证明的内容 | 不能单独证明的内容 |
|---|---|---|
| `@TableBind`、生成 BaseModel | 代码期望的表名、字段访问类型、主键策略 | 目标库表已存在、索引完整、迁移已执行 |
| 当前 Service SQL | 被查询/写入的字段、关联和过滤条件 | 字段物理长度、索引是否存在、真实数据完整性 |
| 目标库元数据 | 实际表结构、约束与索引 | 业务含义和调用权限 |
| 备份文件、历史生成文档 | 形成时的历史信息 | 当前数据库结构 |

`src/main/resources/sql/` 为备份目录，本项目禁止依赖或查询其中 SQL 来推断当前结构。源码中的旧数据库字典也不能当作当前数据库实况。

业务实体源码映射见 [Model 指南](04-Model层开发指南.md)；业务字段语义由各业务专题负责。以下结构事实仅适用于本次核对的本机数据库和时间点，不代表其他部署环境。

## 2. 新增结构的命名与类型原则

以下是设计约束，不是对每个既有字段物理定义的断言：

| 对象 | 设计原则 |
|---|---|
| 业务表 | `siargo_` 前缀，snake_case，名称表达业务对象 |
| 字段 | snake_case；明确单位、时间含义和是否允许为空 |
| 主键 | `BIGINT`，雪花 ID，非自增；浏览器输出为字符串 |
| 关联列 | 清楚表达被引用对象，按实际查询建立索引 |
| 业务时间 | 一般采用 `DATETIME`；纯日期可用 `DATE`，不默认使用 `TIMESTAMP` |
| 状态/标志 | 使用能承载当前业务取值的类型，注释说明含义；不从数值大小推断流程先后 |
| 数量与精确数值 | 按单位、精度、范围选择整数或 `DECIMAL`，不随意以浮点替代 |
| 文本/结构化内容 | 按实际用途、容量、检索和约束选择类型，不把所有内容统一为超长字符串 |

字段的必填、默认值、可空、唯一性是业务决策。不能为了让历史数据“能导入”无依据地改成空串/零，也不能把空值都解释成无效数据。

`tinyint(1)` 的 JDBC 映射可能是 Boolean，生成 Model 和 Service 读取方式应与实际驱动结果一致。数据库类型、Java 类型、SQL 表达式结果和 JSON 类型须分别检查。

## 3. 主子表、关联与约束

主子关系需要同时定义新建、修改、删除、恢复和引用检查。`@TableBind` 与字段名不能证明存在数据库外键；业务上的关联也不自动等于 `FOREIGN KEY` 约束。

设计关联表时应明确：主对象与子对象的归属、是否允许重复、是否需要排序、解绑是否删除实体、软删除时关联是否仍保留。唯一约束不能只依靠浏览器选择器防重，应用层存在性检查与数据库约束也不能相互替代。

当前具体关系请按专题核对：

- [客户供应商与来料图片](09-客户供应商与来料图片.md)：基础资料和图片归属。
- [产品目录与参数](10-产品目录与参数.md)：型号、维度、参数与值的组织。
- [检验报告单](11-检验报告单业务.md)：报告、产品明细、审批与驳回记录。
- [Excel 导入与 PDF 输出](12-Excel导入与PDF输出.md)：模板、关联、生成与发布记录。
- [技术通知单与文件管理](13-技术通知单与文件管理.md)、[设备管理](14-设备管理.md)：主子对象与附件生命周期。

修改关联字段不仅影响写入，还可能影响搜索聚合、列表名称、编辑回显、导出和已有记录的保留。不能以“保存成功”代替完整关联契约核对。

## 4. 索引与查询设计

依据真实过滤、关联、排序和唯一性需求设计索引。先查看目标库已存在的索引，避免重复建立仅名称不同的同等索引。

- 主键与业务唯一键按实际约束确定，不能用普通索引代替唯一性要求。
- 关联列、常用过滤列和排序列评估单列或联合索引；联合顺序需结合查询，而不是机械按字段排列。
- 类型转换、日期函数和模糊查询可能影响索引使用，只有查看实际查询计划后才能声称命中索引。
- 模型 `@JBoltField` 的长度或注释不表示数据库已有对应索引。

复杂查询由 Service 统一组织，使用参数占位。含 `GROUP BY` 的分页要采用正确的聚合分页调用；关键字搜索与聚合并存时，确认过滤不会截断关联聚合结果。[DmsFileService](../../src/main/java/cn/jbolt/admin/siargo/dms/file/DmsFileService.java) 的 `EXISTS` 过滤可作为当前项目参考。

统计文档应明确对象、单位、时间字段、区间边界和删除过滤。现行看板口径见[首页看板与报告统计](15-首页看板与报告统计.md)，不能依据图表标题或方法注释替代实际 SQL。

## 5. 软删除、审计和文件数据

不同模块的删除模型不同，不建立一张通用状态表覆盖所有业务。设计软删除时至少明确：列表是否默认过滤、唯一性如何处理、关联对象如何展示、能否恢复、永久删除前需要哪些引用检查。

审批、驳回、修改和删除记录的业务语义见对应专题。操作者、时间和原因必须由后端按当前身份及操作生成，不能直接信任前端提交的审核人字段。

数据库中的文件 URL 不等于可直接操作的物理路径。路径由 [SiargoStorage](../../src/main/java/cn/jbolt/common/storage/SiargoStorage.java) 解析并验证，业务归属由 Service 校验。数据库回滚不能撤销磁盘删除；物理删除放在真正提交之后，移动操作需要失败补偿，详见 [Service 指南](03-Service层开发指南.md)。

日志和业务表均避免存储明文凭据、完整签名材料或无必要的敏感请求体。对外调用日志的现有内容与管理边界见[接口专题](16-对外接口应用中心与调用日志.md)。

## 6. 结构变更与生成模型

1. 先核实目标数据库、真实结构、现有代码和受影响消费方，列明字段或约束的业务目的。
2. 对需要处理的旧数据明确转换范围与兼容方式，检查新增非空/唯一约束能否满足；不得凭猜测替用户改写历史数据。
3. 数据库插入、更新、删除、DDL、批量导入必须满足当次具体授权。编写代码或方案不自动授权执行数据库变更。
4. 数据库结构落实后按当前生成器配置更新 BaseModel；禁止手工维护生成基类。
5. 核对 Model、Service、请求参数、响应字段、页面、导出和 API，报告实际完成到哪一层。

生成入口见 [ModelGenerator](../../src/main/java/cn/jbolt/extend/gen/ModelGenerator.java)。模型变更流程详见 [Model 指南](04-Model层开发指南.md)。辅助 SQL、分析或验证脚本放在项目 `.codex/` 的对应子目录；正式运行资源仍在项目约定位置，不能依赖开发机的辅助目录发布。

## 7. 需要时如何核实目标数据库

只有任务确需确认实际结构时，才使用当前可用且已授权的只读连接。连接信息从受控配置取得，不复制到文档、终端输出、日志或脚本源码。

可使用以下元数据方式补查目标表；下面的 `SHOW CREATE TABLE` / `SHOW INDEX` 是后续按需核查示例，不属于本次已执行的列元数据查询：

```sql
SELECT TABLE_NAME, TABLE_TYPE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
ORDER BY TABLE_NAME;

SHOW CREATE TABLE siargo_customer;
SHOW INDEX FROM siargo_customer;
```

表名必须是核实后的固定标识符，不由不可信输入直接拼接。核对其他字段可使用 `information_schema.COLUMNS`，按当前 schema 和明确表名限定范围；不要为一次字段变更无目的地导出整库数据。

记录核验结论时明确目标环境、时间与查询范围，并区分“数据库实查”和“源码推断”。查到表名不代表所有数据已正确迁移，静态行数或备份文件检查也不证明实际恢复成功。

## 8. 与本次变更相称的核对

数据库相关修改优先检查字段读写、查询占位、事务边界、关联保留和 JSON 类型。只有关键逻辑确需验证或用户要求时，执行最小必要检查；不固定追加全量测试、导入、备份、打包或重启。

只读核查不能验收真实写入路径。涉及浏览器保存、审批、删除或导入，同样属于数据库写入；服务由用户手动启停，交付时如实区分源码完成、结构落实和运行验证。
